# Аукционы грузоперевозок

Интерфейс перевозчика для торгов по грузам: список аукционов с фильтрами,
карточка аукциона, подача и изменение ставки.

Бэкенда нет — весь API поднят на MSW, состояние живёт в памяти между
перезагрузками страницы (ставка меняет текущую цену, статус участия и
счётчик участников так же, как это делал бы сервер).

## Запуск

```bash
pnpm install
pnpm dev        # http://localhost:5173
```

Прочие команды:

```bash
pnpm test       # vitest в watch-режиме
pnpm test:run   # прогон один раз
pnpm format
pnpm lint
pnpm check      # lint + типы + тесты
pnpm build
```

## Стек и почему он

| Что | Зачем |
| --- | --- |
| TanStack Router | Фильтры живут в URL. Роутер валидирует search-параметры через zod-схему, так что состояние фильтров типизировано и переживает перезагрузку и «поделиться ссылкой». |
| TanStack Query | Кеш серверного состояния, чтобы не городить руками загрузку/ошибку/инвалидацию после ставки. |
| MUI | Готовая типографика и формы; тема переопределена под макет. |
| react-hook-form + zod | Одна и та же схема валидации ставки описывает и форму, и правила шага/минимума/максимума. |
| zustand | Только для UI-состояния, не относящегося к серверу: открытость панели фильтров и тосты. |
| MSW | Сервис-воркер отдаёт API в дев-режиме и он же переиспользуется в тестах стора. |

## Структура

Feature-Sliced Design, слои снизу вверх:

```
src/
  app/        провайдеры, роутер, тема, queryClient
  pages/      auctions, auction-detail, place-bet
  widgets/    app-shell, bets-panel
  features/   auction-filters (URL-состояние), price-bet (схема ставки)
  entities/   auction (view-модель карточки)
  shared/     api, mocks, ui, lib, config
```

Правило импортов обычное для FSD: слой знает только про те, что ниже него.

## Решения, которые стоит пояснить

**Фильтры — источник правды в URL.** `features/auction-filters/model/searchParams.ts`
описывает zod-схему search-параметров; каждое поле с `.catch(...)`, поэтому
битая ссылка не роняет страницу, а откатывается к дефолту. Оттуда же
`buildAuctionListRequest` собирает тело запроса — компоненты не знают формата API.

**Черновик фильтров синхронизируется без `useEffect`.** В `AuctionFilters`
сравнивается предыдущее значение пропа и состояние правится прямо во время
рендера — это дешевле лишнего коммита и рекомендованный React-паттерн.

**OpenAPI DTO отделены от модели интерфейса.** Клиент обращается к
`/api/v1`, проверяет обязательную структуру ответа и преобразует `data/meta`,
detail и `bets` в модель приложения в `shared/api/auctions/adapters.ts`.
`entities/auction/model/viewModel.ts` отвечает только за готовые к отрисовке
строки карточки.

**Мелкая типографика — через варианты темы.** `body2` / `caption` / `overline`
заданы в `app/theme.ts`; числовых `fontSize` в компонентах нет.

## Тесты

Покрыта логика, а не разметка: форматтеры, view-модель карточки, схема
валидации ставки, четыре метода API, адаптация OpenAPI DTO и мок-стор
(контрактные фильтры, пагинация и правила ставки).

```bash
pnpm test:run
```

## Что не сделано

- Нет реальной авторизации: перевозчик захардкожен в моках.
- Нет виртуализации списка — на текущем объёме данных не нужна.
- Нет e2e; при живом бэкенде первым делом добавил бы сценарий «подать ставку».
